# 蒸汽港的下一班

这是《文明航程》成员 C 的独立离线教学原型。一次演练约 3 至 5 分钟。玩家引用材料排定班次，看见货主、原班船员、替班组和下一班各自受到的影响，最后留下安排与反思。成员 C 负责实践与讲解，场景使用本地标识 `c_steam_port_pilot`。

## 在本机启动

在仓库根目录打开终端。Windows 已安装 Python 3 时运行以下命令。

```powershell
py -3 -m http.server 8765 --bind 127.0.0.1 --directory docs/prototypes/c-practice
```

macOS 或 Linux 可将 `py -3` 换为 `python3`。如果已进入本 README 所在目录，省略 `--directory docs/prototypes/c-practice` 即可。在浏览器打开[本机演练](http://127.0.0.1:8765/)，保留终端以便刷新，结束时按 Ctrl+C。页面通过 HTTP 读取同目录的情境 JSON 和脚本，直接双击 HTML 无法加载完整体验。只需要静态文件服务与现代浏览器，运行时使用本机存储，无需安装前端依赖或配置 API Key。

## 课堂演示

1. **问题与材料**　填写本轮优先目标，打开材料的“出处与局限”。主动加入 K1 和至少一张 S 卡。课堂卡给出判断视角，情境卡提供演练条件。
2. **制定安排**　对照三份班表，选定一份。可展开两位船员的预写意见。说明引用的材料如何影响判断，点选主要承担者，并写下预期影响。预览时固定初始目标与 v1。
3. **影响预览**　看货船停在哪一档、原班是否多值一格、替班人员有无上岗、储备箱还剩几个。图下的四项文字和旁边的四方交接说明给出相同结果。点击“打开共同维护需求”，所有人收到同样的 2 单位维护需求。
4. **成果与反思**　对照目标、第一版理由、预期与新信息，写出理解和仍有人承担的代价。可以改选一次、保持原案，或写下仍需查找的材料。修订后的 v2 预览直接通向成果。保持和证据不足各只产生一条反思。
5. **交接**　成果页可展开各版原始记录，核对余量与缺口，导出 JSON。中途也可导出草稿。刷新恢复同一浏览器、同一地址的本机记录。“重新开始”需要再次确认。

**可以这样讲给观众。** 我原先想让货主准时收货，也保住原班轮休，所以用 2 单位储备调用替班。港区图里，工作转到了替班组，下一班手上只剩 1 单位。拆开维护单后才发现还缺 1 单位。如果改为常规轮班，维护预留后还能剩 1 单位，但货主要多等一格。如果坚持，交接簿会保留这个缺口。请观众看看自己的目标和最初相比有没有变化，并说明理由。演示时请标明代填的内容属于示例。

## 课程依据与案例规则

K1 转述 Week 5–6 第 4–6 页的隐形劳动、仁义和义利取舍。“课程依据与设计转化”另列 Week 5–6 第 13、15 页的后来者责任与人的分配判断，Week 4–5 第 6–7 页的知识流动与成功判断，以及 Week 1–2 第 28、31 页的独立判断与道德影响。卡片列出课程文件名，页码含封面。这里沿用配套审核稿提供的中文转述。港口安排是成员 C 对“知行合一”的教学转化，若引用具体哲学命题仍需另给原典。程序只带转述与定位信息。

S1、S2、S3 分别是虚构交付单、值班表与资源簿。两位船员的意见均为预写演示，可不同意。规则中的格与单位只表示抽象时段和资源。所有玩家从 3 单位储备起步，约定交付窗口为 1 格，有一组可调用的替班人员。

| 选项 ID | 安排 | 交付延迟 | 原班额外执勤 | 替班组 | 替班支出 | 本轮储备 | 预留维护后余量 | 维护缺口 |
| --- | --- | ---: | ---: | --- | ---: | ---: | ---: | ---: |
| `regular` | 常规轮班 | 1 格 | 0 格 | 未调用 | 0 | 3 | 1 | 0 |
| `rush` | 原班加速 | 0 格 | 1 格 | 未调用 | 0 | 3 | 1 | 0 |
| `relief` | 增配替班 | 0 格 | 0 格 | 接手工作 | 2 | 1 | 0 | 1 |

本轮储备等于初始储备减去替班支出。预留后的余量为 `max(0, 本轮储备 − 维护需求)`，缺口为 `max(0, 维护需求 − 本轮储备)`。共同通知在第一次预览后打开一次，修订沿用同一信息、从初始储备重新计算。缺口可留待交接。谁被玩家点名和玩家写了多少字，都不影响模拟结果。

## 文件与记录

| 文件 | 用途 |
| --- | --- |
| `index.html`、`port.css` | 页面入口、纸面交接簿、键盘焦点与窄屏排版 |
| `scenario.json` | 版本、问题、四张材料、课程定位、预写观点、规则与三种安排 |
| `model.js` | 规则计算、版本链、反思与草稿恢复校验 |
| `views.js`、`harbor.js` | 四页内容、二维港区图、交接单和逐版回看 |
| `app.js` | 本机读取与自动保存、导航、确认重置和下载 |

草稿与导出共用一份 JSON 结构。浏览器存储键为 `civilization-voyage.c-practice.steam-port`。本轮 `schemaVersion` 为数字 1，`scenarioVersion` 和 `rulesVersion` 均为字符串 `1.0`。本地模型供评审与交接使用。

| 字段 | 本轮语义 |
| --- | --- |
| `moduleRole / scenarioId / scenarioVersion / rulesVersion` | 成员身份、教学情境及其计算版本 |
| `question / goal / initialGoal` | 当前问题、草稿目标、首次预览时固定的目标 |
| `materials / upstreamViews / handoff` | 材料字典、预写意见及来源交接信息。意见和演示输入标为 `demo_preset`，团队确认状态为 `pending` |
| `planRecords[]` | 唯一记录 `id`、版本、前版记录 ID、选项 `planId`、选中的本地材料 ID、当时理由、承担者、预期、时间、`ruleInputs` 和直接结果 `effects` |
| `maintenanceRevealed / maintenanceObservations[]` | 通知揭示状态；按唯一 `planRecordId` 追加维护需求、余量和缺口。新信息独立保存，v1 快照保持原样 |
| `reflections[]` | 唯一 ID、`basedOnPlanRecordId`、`resultPlanRecordId`、决定、理解、代价、回应、未解决事项与时间。缺证分支在 `response` 说明待补材料 |
| `selectedPlanRecordId / stage` | 当前有效方案记录与页面。展开历史记录只供阅读 |
| `form / reflectionDraft` | 未提交输入，可在刷新后继续。成果保存后与当前方案及反思对应 |

v1 的 `previousPlanRecordId` 为 `null`，v2 指向 v1 的唯一记录 ID。反思基于 v1，`resultPlanRecordId` 指向最终采用的记录。选项名 `regular / rush / relief` 只标识班表。改选原班表会要求写坚持理由，按 `keep` 保存。每次至多两版安排、一条收束反思。

恢复时校验版本、材料字典、引用、快照、维护观测、状态与版本关系。损坏或不兼容会显示提示，允许保留原数据、下载副本或确认清除。浏览器不允许存储时，页面提示仅本页暂存，仍可导出。用相同地址和端口才能接续同一份草稿。导出为本地 JSON，本轮没有导入流程。

**接入 A 与 B。** 先由团队确认同一情境。A 可提供 `revised_question` 及 `sources` 中经过选择的材料，保留出处、可支持的范围和局限。B 提供有来源的观点、仍存在的分歧及确认范围。A 当前示例“团圆微展”与蒸汽港是不同题材，其 M 编号、预算和问题不能直接移作港口证据。个人问题卡的确认仅属于本人。本原型使用演示输入，未绑定任何真实航程 ID。

**输出到现有记录接口。** D 可在靠港选位、落印后的环节挂载交接簿，并决定组件、状态传递和旧记录兼容方式。`POST /voyages/{vid}/records` 只接受既有的 `kind / text / classification / sources / material_ids / version / access`。响应提供真实 `id` 和 `voyage_id`。教学创作内容可按接口既有类别 `creative` 传递，由 D 按团队对具体材料的归类确认；`access` 沿用 `private`。

| 原型数据 | D 需要建立的对应关系 |
| --- | --- |
| 问题、`handoff`、本地材料 K1/S1–S3 | 关联真实 voyage 与该航程的 material/fragment 记录。将玩家实际引用的 `selectedMaterialIds` 映射到这些记录的真实 `id`，再填 `material_ids`。`Source.id` 与 material 记录 ID 的语义不同。课程文件未提供公开链接，需核实授权及来源元数据后再填接口的 `Source` |
| 每个 `planRecords[].id`、行动与理由 | 按需生成 `choice`，保存本地方案记录 ID → 真实 choice ID 映射。重试时应按映射核对已写记录 |
| 初始目标、所选材料、各方影响、维护观测与缺口 | 生成 `artifact` 的可读 `text` 及对应来源。完整结构化快照的保存方式由 D 约定 |
| `reflections[]` 与 v1/v2 关系 | 生成 `reflection`。`basedOnPlanRecordId` 和 `resultPlanRecordId` 需映射到真实记录，在适配层约定持久化与读取顺序 |
| 只有 `version` 数字的旧记录 | 缺少关系时显示为孤立版本，不凭相同选项名推导上一版 |

后端输入模型禁止额外顶层字段。不要直接把 `effects`、`previousPlanRecordId` 或整个导出对象提交给该接口。自由结构的 `world` 也不能保证版本历史可靠保存。本地评审提供操作截图及真实浏览器验证结果，截图均使用虚构演示输入，单独存放。
